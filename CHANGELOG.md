### Added

- **MCP tool `get_agent_status` + persisted `agents.last_connected_at`** (PRY-030, Slice 2 of [MCP Server + Tool Surface](https://github.com/hivemine-ai/hive-vault) — third and last deferred tool, closes the v0.1 catalog at 8/8): new tool that returns the presence (`online` / `offline`) and last-connected timestamp of an agent visible to the caller. Output shape `{ participant_id, presence: 'online' | 'offline', last_connected_at: string | null }`. **Effective presence** = `presence.online && participantState.state === 'active'` — a `suspended` agent that still holds an open session is reported as `offline` (the internal `suspended` state never crosses the wire, per the product spec Tool 7 privacy). Online path derives `last_connected_at` from `max(presence.sessionsSubscribedAt)` so a fresh re-subscribe wins over older sessions; the individual session timestamps NEVER reach the wire (defense-in-depth privacy, [Waggle Pipeline + Presence Registry](https://github.com/hivemine-ai/hive-vault) § `PresenceSnapshot.sessionsSubscribedAt` + this spec § Tool 7 Privacy). Offline path reads the persisted `agents.last_connected_at` (or `null` if the agent never connected). Visibility-denied collapses to `RECIPIENT_UNREACHABLE` (`-32004`) for uniform privacy — indistinguishable from a non-existent participant, same as `list_agents` and `send_message`. **DB migration `20260501120000_add-last-connected-at-to-agents.ts`** adds the new column (`text` / nullable, portable across SQLite TEXT and Postgres `timestamptz`) — backwards compatible (existing rows stay `NULL` until first subscribe). The column is populated by a non-blocking side effect in `presenceRegistry.subscribe`: for `worker` and `scout` callers the registry fires `Promise.resolve().then(() => participantsRepo.updateAgentLastConnectedAt(participantId, tNow)).catch(logger.warn)` AFTER the `onSubscribed` hook returns — `hivekeeper` callers are skipped (they have no `agents` row), and a rejected UPDATE is logged at `warn` (per [ADR-013](https://github.com/hivemine-ai/hive-vault)) without aborting the subscribe (the subscription is already returned to the caller). New repo method `participantsRepo.updateAgentLastConnectedAt(agentId, timestamp): Promise<void>` lives on `ParticipantsReadRepo` (transport-layer side effect, not an admin operation — same convention as `listAgents` post-PRY-029); silent no-op when the row vanishes mid-flight (deleted-agent race) — the warn is captured in the structured log. **N1 nice-to-have inheritance from PRY-029 resolved**: the cast escape hatch `state: agent.state as 'active' | 'suspended'` in `views/agent-list-view.ts` is replaced with `assertWireState()` defense-in-depth — a `revoked` agent reaching projection now throws `INVALID_INPUT { subCode: 'agent_revoked_in_projection' }` instead of being silently relabeled, surfacing the bug loudly upstream of the wire (the handler post-filters `revoked` before projection — assertWireState is the type-narrowing gate). Operational note for deploys: this PRY adds a migration; per the established pattern (lesson PRY-027), the server boot does NOT auto-migrate. Run `node packages/cli/dist/main.js migrate up` BEFORE restarting the server in any environment (dev, staging, prod) — without the migration, `get_agent_status` will fail at runtime trying to read a column that does not exist. ### Fixed

- **`send_message` idempotency key now scoped by `(sender, recipient, key)` instead of `(sender, key)`** (PRY-027, closes [INC-2026-001](https://github.com/hivemine-ai/hive-vault) finding #4, sev-3, implements [ADR-018](https://github.com/hivemine-ai/hive-vault)): a client that called `send_message` with `{recipient: A, key: "X"}` and then `{recipient: B, key: "X"}` would receive `replayed: true` for the second call with the message id of the first — the message to recipient B was never delivered, with no error surfaced to the client (silent message loss). Internal validation 2026-04-27 (iter10/11) reproduced the regression. The `idempotency_keys` table primary key is now `(sender_id, recipient_id, key)` (was `(sender_id, key)`); `idempotencyLookup` and `insertIdempotencyKeyOrConflict` in `domain/cells/send.ts` accept `recipientId` as an explicit argument, and the three call sites (pre-TX lookup, in-TX insert, post-conflict winner-lookup) all pass `input.recipientId` from the existing `SendMessageInput`. Aligned with HTTP / Stripe-style idempotency conventions: the same client may safely reuse the same `idempotency_key` string across distinct recipients without colliding. Backward-compat preserved for the same `(sender, recipient, key)` tuple — the second call still returns `replayed: true` with the original `messageId`. **Migration note**: drops and recreates the `idempotency_keys` table with the new 3-column primary key. In-flight idempotency state is lost (rows are TTL 24h, no production data preserved); the worst-case for a client mid-retry is overshoot benign (the message is sent twice) versus the silent loss of the status quo. The `idx_idempotency_keys_created (created_at)` index is preserved post-migration so the future purge job continues to function. The wire schema of the `send_message` tool is unchanged — clients keep sending `{idempotency_key: "..."}` as before; `recipient_id` already travels in the `recipient` field and is resolved to `UUIDv7` in the handler before the domain layer sees it. No breaking change to the external contract. Adds 4 unit tests in `domain/cells/send.test.ts` (cross-recipient no-replay, backward-compat same-recipient replay, cross-sender no-collision, two concurrent senders to the same recipient with the same key) plus 1 test confirming the purge mechanism (DELETE WHERE created_at < cutoff) still works under the new schema. **674 server tests + 83 cli tests, all green** (+5 new from PRY-027). Closes the last sev-3 architectural cleanup of INC-2026-001.
- **`send_message` now accepts `action: null` in input as equivalent to omitting the field** (PRY-026, closes [INC-2026-001](https://github.com/hivemine-ai/hive-vault) finding #7, sev-3): the MCP tool `send_message` previously rejected `{action: null}` with `-32602: invalid input` (`Expected object, received null`), even though the wire output (read) returns `action: null` whenever no action is attached — so a client that read a stored message and re-sent it verbatim was hit with a footgun. The schema is now `z.record(z.unknown()).nullish()`; the handler treats `null` and omitted identically (downstream `Sender.sendMessage` receives no `action` key, and `domain/cells/send.ts` coerces it to `null` in storage as before). Wire output is unchanged. Round-trip is now symmetrical: client can read a message and re-send the object verbatim. Backward-compat is strict — clients that omit `action` keep working unchanged. Per [ADR-017](https://github.com/hivemine-ai/hive-vault). Adds 5 unit tests in `transport/mcp/tools/send-message.test.ts` covering the schema acceptance (null literal, omitted, populated object) and the handler equivalence (null and omitted produce identical sender-input shape). Note: the handler guard was tightened from `!== undefined` to `!= null` to exclude both null and undefined under `exactOptionalPropertyTypes` — the previous strict-undefined check would have leaked `null` into the typed `Sender.sendMessage` input. **662 server tests + 83 cli tests, all green** (+5 new from PRY-026).
- **MCP error envelope now carries structured field info via `data` field** (PRY-023, closes [INC-2026-001](https://github.com/hivemine-ai/hive-vault) finding #5, sev-3): the JSON-RPC error envelope `-32602: invalid input` previously omitted any indication of which input field violated which rule, forcing clients with multi-field tool calls (e.g. `send_message` with `recipient`, `type`, `body`, `ttl_ms`) to bisect their input client-side by trial-and-error re-submission. Per the JSON-RPC 2.0 spec the error object accepts an opaque-to-spec `data` field for method-specific structured info; the mapper now populates it on the `ZodError` branch with `{issues: [{path, code, message}]}` — zod-native shape so clients can map directly into their error UIs. **F-S2 invariant preserved** (PRY-006): `wire.message` continues to be a string-literal from the mapping table ("invalid input"); `data` is purely additive. **Domain `INVALID_INPUT` paths stay opaque** (CellError, WaggleError with subCodes like `caller_has_no_cell`, `message_ids_too_many`, `limit_not_positive`): only `ZodError` populates `data` — domain subCodes never cross the wire boundary. **Privacy invariant**: a whitelist sanitizer copies only the three fields `{path, code, message}`. Notably `received` (the value the caller sent) is NEVER echoed — risk of PII or credential leakage if the input was sensitive, plus echo-amplification on logs that persist responses. Path arrays are joined with `.` (zod-native): root-level errors yield `""`, nested objects yield `"recipient.email"`, array indices yield `"message_ids.3"`. Backward-compat: clients that only read `{code, message}` keep working — `data` is optional per spec. The MCP SDK propagates `data` to the wire automatically (verified empirically against `@modelcontextprotocol/sdk@1.29.0` `protocol.js` line 400: `...(error['data'] !== undefined && { data: error['data'] })`). Adds 10 unit tests in `transport/mcp/error-mapper.test.ts` covering AC1–AC6 from the PRY (schema simple, nested path, multi-issue, domain opaque preserved, privacy `received`-never, backward-compat for non-Zod, whitelist key-set, root-level empty path). **648 server tests + 83 cli tests, all green** (+10 new from PRY-023).
- **`mark_read` no longer fails the whole batch on a single malformed UUIDv7** (PRY-022, closes [INC-2026-001](https://github.com/hivemine-ai/hive-vault) finding #2, sev-3): the MCP tool `mark_read` previously rejected the entire batch with `-32602: invalid input { subCode: 'message_id_malformed' }` if any single id in `message_ids` failed the UUIDv7 regex pre-handler check. A client with 199 valid ids + 1 malformed id lost all 199 ack operations and had to re-validate client-side before retry. Now malformed ids are routed to the existing privacy-preserving `ignored` catch-all bucket — the same opaque category that already absorbs unknown ids, ids belonging to another cell, already-read ids, and expired ids. Callers cannot distinguish "malformed" from "unknown" by design (no leak via response shape). Input order is preserved across the merged response so callers can correlate offsets. The schema (`z.array(z.string())`) is unchanged; the validation lives entirely in the tool layer (`packages/server/src/transport/mcp/tools/mark-read.ts`) — the domain `Reader.markRead` continues to receive only valid UUIDv7 strings (lowercased) and is otherwise untouched. Edge case: a batch with only malformed ids returns `{ marked: 0, ignored: [...all] }` as success (no DB roundtrip), consistent with the principle "no leak via error vs success differentiation". Audit of callsites across `packages/{server,cli,client,shared}` confirmed zero internal callers were depending on the fail-fast `-32602` as a control mechanism, so severity remains sev-3 (no retroactive escalation). ### Security (v0.1.0 progress)

- **F-S2 wire-error privacy uniformity** (PRY-006): `error-mapper.ts` constructs the wire `message` from a fixed string-literal table, NEVER from `err.message`. Tests assert the `subCode` literal is absent from `wire.message` for every code that has subCodes (`RECIPIENT_UNREACHABLE`, `INVALID_INPUT`, etc.). Closes the F-S2 hardening flagged by the `/security-review` of PRY-003 (CellError default `Error.message` was `"<CODE> (<subCode>)"` — a naive pass-through to the client would have leaked subCodes).
- **F-S3 action JSON depth check** (PRY-006): `transport/mcp/action-safety.ts::ensureSafeAction` rejects messages whose `action` payload exceeds 32 levels of nesting before exposing to the MCP client (the first point in the pipeline where `JSON.parse(action)` runs, since Cell Store treats `action` as opaque). Iterative DFS — no recursive depth-of impl. Tests cover deep object, deep array, and broad+deep mix. Wire error: `INVALID_INPUT { subCode: 'action_too_deep' }`.
- **Authorization header + message body redacted in logs** (PRY-006): `createLogger({ redact })` now defaults to masking `authorization`, `req.headers.authorization`, `*.body`, `*.params.body`, `*.arguments.body` with `[redacted]`. Operators can override `LoggerOptions.redact`. Closes the spec invariant that JWTs and message contents NEVER appear in logs.
- **TOCTOU send/cascade fix** (PRY-010): `sendMessage`'s recipient-cell guard now runs INSIDE the message INSERT transaction. On Postgres the SELECT takes a `FOR SHARE` row lock so a concurrent `closeCellsByOwner` UPDATE blocks until the send commits, then the send observes `state='closed'` and aborts with `RECIPIENT_UNREACHABLE`. SQLite's single-writer model serializes implicitly. Closes the bounded race flagged by the `/security-review` of PRY-003.
- **Per-listener exception isolation in `events.emit`** (PRY-010): each subscriber now runs in its own try/catch — both synchronous throws AND async (Promise) rejections are caught and forwarded to a per-emit `onError` sink, never propagating to the caller or surfacing as `unhandledRejection`. A failing listener cannot prevent others from running and cannot roll back the message INSERT.
- **Always-allow `stubVisibilityEngine` replaced by the real engine in production wiring** (PRY-004): the composition root now constructs `createVisibilityEngineForProduction` so every `sendMessage` call evaluates the product matrix against the recipient and audits denials. The stub remains exported for Cell Store unit tests only; production code paths must use the factory. Closes the bounded "stub-as-engine" surface that PRY-002 + PRY-003 shipped with.
- **Privacy-uniform denials at the wire** (PRY-004): every `canSend` denial collapses to a boolean `false` for the caller (Cell Store maps it to `RECIPIENT_UNREACHABLE`). The discriminating `reason_code` (e.g. `worker_to_other_owner_worker`, `recipient_not_found`, `cross_hive`) lives only in the audit log, never on the wire — preserves the anti-enumeration property declared by the product spec.
